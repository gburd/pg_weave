# Result: what a second, vector-major copy of the codes would cost on disk

Date: 2026-10-04. Task `vmajor`, deliverable 1 (bytes only).

There are two findings here, and the first matters more than the question that was
asked:

- **(A) The SHIPPED index is larger than the ratified shape says.** Built with
  `CREATE INDEX ... USING weave (d, v)` at 4 bits, it measures **534 / 789 / 789 / 1,045
  B per vector at 384 / 768 / 960 / 1,024-d**. The "512 B/vector = 0.064× HNSW" quoted
  across the tree is `bits × dim / 8`, i.e. the code bytes from arithmetic. It is not a
  built index. Against pgvector HNSW measured on the same vectors, the shipped index is
  **0.261× / 0.193× / 0.096× / 0.128×**, so it **already fails the 0.15× storage gate at
  384-d and 768-d**. It passes at 960-d and 1,024-d, with less margin than claimed. The
  cause is in the layout: the writer emits **one page per strip**, so each 32-lane
  block's centroid strip (dim/2 bytes) takes a **whole 8 KB page**. That is **256 B per
  vector at every dimension**, which is 24–48 % of the index (48 % at 384-d).
- **(B) A second vector-major copy fails the gate at all four dimensions.** Measured
  on top of today's layout, the cheapest copy (dense, no centroid, sharing the
  directory's scale/norm) gives **0.356× / 0.288× / 0.159× / 0.194×**. Even the
  information floor of dim/2 bytes per vector gives 0.155× at 960-d. **The old
  sentence "(b) forfeits the storage gate" was right, but it was never measured, and it
  gave the wrong reason.** At 384-d and 768-d, two copies of 4-bit codes cannot fit
  under 0.15× this HNSW **in any layout**: dim bytes per vector is more than the whole
  budget. At 960-d and 1,024-d a copy fits only after the centroid lever below.

> **SUPERSEDED IN PART 2026-10-05: finding (A)'s numbers describe weft v3, which no
> build writes any more.** The lever below was built as vector weft **v4** (the
> centroid strip shares its block's last lane page; `doc/specs/VECTOR_CHANNEL.md`
> §7.1 "v4"). The built index now measures **278.0 / 533.3 / 533.3 / 789.3 B/vector
> = 0.136 / 0.130 / 0.065 / 0.096× HNSW**, which **passes 0.15× at all four dims**.
> See "Measured: the centroid lever, built (v4)" at the end of this file. Finding (B)
> is unchanged in kind (a second copy still fails at 384/768-d for the arithmetic
> reason stated there); its "lever + lean" column is now measurement + projection
> rather than projection + projection.

Setup, per dimension: N gaussian vectors, L2-normalized, generated by a seeded C
generator inside the script (seed = dim). Each value is rounded to float32 before
printing, so `wvec` and `vector` parse identical values. The same stream is loaded
into `tw (id, d wdoc DEFAULT to_wdoc('v'), v wvec(dim))` and `tp (id, v vector(dim))`,
and three rows are compared coordinate by coordinate before any index is built. Then:

```sql
CREATE INDEX tw_idx  ON tw USING weave (d, v) WITH (bits = 4);
CREATE INDEX tp_hnsw ON tp USING hnsw (v vector_cosine_ops) WITH (m = 16, ef_construction = 64);
```

Weave bytes come from `weave_index_size_detail()`. Lane pages and centroid pages come
from `weave_vec_strips()`, counted by its `centroid` flag. Before printing, the script
asserts four things: the two code-page counts agree, the size buckets sum to
`pg_relation_size`, `sum(nvec) = N`, and every weft is `bits = 4, dim = D`. HNSW bytes
are `pg_relation_size('tp_hnsw')` after `CREATE INDEX` has returned. Run 1's
`remote/` pull came back empty, so its rows are taken from `script.log`, where the
script prints the same TSV. `bench/aws/out/` is gitignored, so every number used here
is reproduced below.

¹ Everything outside the four `vector_*` buckets: the lexical weft of a one-token
wdoc, the metapage and the channel descriptor. `vector_meta` is one page (0.04
B/vector) and is not shown. One segment at every size.

The page model is exact, and that is what licenses the projections in (B) and (C).
A strip page carries 8,160 payload bytes and a 12-byte header, and stores 16
bytes per coordinate per block at 4 bits, so it holds 509 coordinates.
`weave_index_size_detail`'s `free_bytes` for `vector_codes` matches
`Σ (8,160 − 12 − used − 4) × nblocks` to the byte at every dimension. At 1,024-d,
for example: lane pages of 509 + 509 + 6 coordinates, with 0 + 0 + 8,048 free, plus
a centroid page with 7,632 free, gives 15,680 × 6,250 = 98,000,000. The table shows
98,000,000.

**Flat in n.** n = 200,000 and n = 50,000 agree to within 0.3 %. The only difference
is a few fixed pages per index (metapage, `vector_meta`, the first directory and warp
pages) spread over fewer rows. Every vector cost is quantized by the 32-lane block,
so it does not drift with n. This is the second scale that hard rule 11 asks for.

### The HNSW denominator, checked

- **It is a completed build, not a pre-sized relation.** Every size is
  `pg_relation_size` after `CREATE INDEX` returned. A `pageinspect` census of every
  non-meta page (`(pd_lower − 24) / 4` items, two items per element) finds exactly
  8 / 4 / 2 / 2 items on **every** page (min = max), and elements = N exactly, at
  n = 50,000. So the index holds **4 / 2 / 1 / 1 elements per page**, and its size is
  `ceil(N / per_page) + 1` metapage. That is why the denominators are round powers of
  two. At 960-d and 1,024-d the element (4·dim bytes of vector) plus its level-0
  neighbour tuple (2m = 32 TIDs) is over half a page, so each element costs a whole
  8 KB page.
- **Why GIST-1M measured 8,056 and not 8,192.** pgvector stores an exact duplicate
  vector as an extra heap TID on the existing element, not as a new element. The
  duplicate control shows it directly: 20,000 unique 960-d vectors plus 2,000 exact
  copies built **20,000 elements in 20,001 pages**. `gist_base.fvecs`, hashed on the
  instance, has 1,000,000 rows, 10 all-zero (dropped by the loader), 999,990 non-zero
  and **982,693 distinct**. That is 17,297 duplicate rows, 1.7 %. At one element per
  page this predicts 982,694 pages. The three recorded builds have 983,457 / 983,445 /
  983,445 pages (`size.tsv` of `pgweave-20260912-205358`, `-211128`, `-20260913-180623`).
  **A residual of ~760 pages (0.08 %, ~6 B/row) is unexplained here.** It moves no
  ratio below by more than 0.001. So the two figures agree: about 8,192 B per
  *distinct* vector, divided over the *rows* of a corpus that is 1.7 % duplicate.
- **Which denominator each ratio uses.** Every ratio in this file divides by the
  **same-run HNSW on the same vectors** (2,048 / 4,096 / 8,192 / 8,192), except the
  explicitly labelled "vs 8,056" column. The 8,056 figure is the recorded GIST-1M
  build and is the denominator of every earlier Phase V document.
- HNSW is at **defaults only**, not at the best-recall point of an `m` ×
  `ef_construction` sweep that `doc/PHASES.md`'s storage gate asks for. A larger `m`
  makes HNSW bigger, so this choice can only make the weave ratios look worse.

## (B) The cost of a second, vector-major copy

**What a copy has to carry.** In the shipped format, per-lane `(scale, norm)` are not
in the code pages. They live in the directory record (`WeaveVecDirRec.lane[]`,
`include/weave/vecpage.h`, 8 B/vector, included in the 9.2 B `dir` column). The
centroid **is** in `vector_codes`: it is the 256 B/vector strip. A vector-major copy
built for per-lane reads **does not need the centroid**. The centroid is read only by
the (B3) block bound, which measured 0.00 % pruning, and the block-major copy keeps
it anyway. A per-lane distance does need `(scale, norm)`, and there are two ways to
get it: read them from the shared directory (one directory page covers 28 blocks =
896 lanes), or inline them at 8 B/vector. Both variants are priced:

| variant | what it holds | 384 | 768 | 960 | 1024 | basis |
|---|---|---:|---:|---:|---:|---|
| verbatim | a second copy of today's code weft + directory | 521.2 | 777.2 | 777.2 | 1,033.2 | measured |
| **lean** | dense lanes `floor(8148 / (dim/2))` per page; no centroid; shares the directory's scale/norm | **195.0** | **390.1** | **512.0** | **546.1** | projected² |
| full | dense lanes with inline scale/norm (dim/2 + 8 B), plus its own centroids packed `floor(8148 / (dim/2 + 12))` per page | 210.8 | 421.7 | 527.1 | 562.2 | projected² |
| floor | dim/2 bytes, zero overhead | 192 | 384 | 480 | 512 | arithmetic |

² From the page model, which `free_bytes` reproduces exactly. Lanes per page are
42 / 21 / 16 / 15. A copy whose pages each held one block's lanes would cost the
same as today's lane strips (256 / 512 / 512 / 768) and would gain nothing. A copy
with no page-aligned blocks is the lean row.

## The lever: one page per strip

`src/vector/vecwrite.c` writes "ONE page per strip; the greedy several-strips-per-page
packing sect. 7.1 leaves to the writer is not implemented". The centroid strip is one
lane's worth of coordinates, dim/2 bytes. It gets a whole page per block, which is
8,192 / 32 = **256 B/vector of which 6–16 B is data**.

- **Recovery from moving the centroid strip:** about **240–256 B/vector at every
  dim**. There are two ways to do it:
  1. **Pack the centroids, `floor(8148 / (dim/2 + 12))` = 39 / 20 / 16 / 15 per
     page.** That costs 6.6 / 12.8 / 16.0 / 17.1 B/vector, a recovery of 249 / 243 /
     240 / 239.
  2. **Put the centroid in the free tail of the block's last lane page.** That page
     has 2,004 / 4,004 / 932 / 8,052 free bytes against the 204 / 396 / 492 / 524 the
     centroid needs (header included), so it fits at all four dims. The cost is zero
     pages, a recovery of the full 256. The index becomes **278 / 533 / 533 / 789
     B/vector**, which is the "centroid lever" column above.
- **Second, smaller lever:** coordinate-split waste on the lane strips. At 1,024-d a
  block needs 16,384 B and two pages hold 16,296, so the third page holds 6
  coordinates (96 B) and wastes 8,048. Packing lane strips across blocks would take
  1,024-d lanes from 768 to about 515 B/vector. At 384 / 768 / 960-d the lane strips
  are already 75 % / 75 % / 94 % full.

Either lever changes what a strip page may hold, and the reader's seek/validation and
`weave_check()` would have to change with it. **[2026-10-05: option 2 is built (weft v4)
and measured below. The lane-strip coordinate-split lever is not.]** **The writer's comment already calls
this waste "real and recorded rather than claimed away".** Until today it was recorded
nowhere in bytes per vector.

## What this does not tell us

- **Whether per-lane reads make the fused scan faster.** That is the work-replay
  measurement, a separate task. This file prices the copy and does not say whether it
  is worth buying.
- **The weave side on a real corpus.** Weave's vector bytes do not depend on the data
  at fixed (n, dim, bits), but its lexical bytes do. Here the wdoc is one token, and a
  real document adds lexical-weft bytes that HNSW does not carry. The HNSW side does
  depend on the data, through duplicates (above).
- **More than one segment.** Every index here is a single freshly built segment.
  Inserts, merges and VACUUM rewrites add partial blocks, directory and warp pages per
  segment. None of that is measured.
- **n = 1M for weave.** The costs are flat between 50k and 200k and quantized per
  block, so 1M is predicted to match to well under 1 %. That is a prediction, not a
  measurement.
- **The dense vector-major rows, and both levers.** These are projections from a page
  model that reproduces the measured free space exactly. No such writer exists.
- **HNSW at its best-recall configuration.** Only defaults were measured, and see above
  for which way that cuts.

- **Measured matches predicted to within 0.3 B/vector at every dim and both scales.**
  The prediction was v3 minus exactly 256.0 B/vector, which is one 8 KB page per

  11,225,000 / 22,525,000 / 2,725,000 / 47,025,000 at n = 200k. That is

  `align4(12 + 16 × n_last)` on the last lane page, computed independently, and it
  matches at all four dims. So the layout on disk is the layout the spec describes,
  not just one of the same size.
- **The 0.15× storage gate now passes at all four dims.** The tightest margin is
  384-d at 0.136×: 29 B/vector of headroom against a 307 B/vector budget. That
  headroom is smaller than the lexical bytes a real document adds (see "What this
  does not tell us" above). **A real-corpus 384-d index could still fail; that is
  unmeasured.**

  bytes per vector, more than the whole budget. At 960-d, the measured v4 index plus
  the projected lean copy is 533.3 + 512.0 = 1,045.3 B/vector = **0.128×**, still a

### Cold latency: faster, because the scan stopped reading the centroid's page

Same job, same binary (v4 `.so`). The arms are a v3 index, built under the v3 `.so`
and dual-read, and its v4 rebuild: 200,000 × 960-d at 4 bits, same vectors. Both
answer 8 queries identically, checked before timing. Each sample is `sync`,
`drop_caches`, a PostgreSQL restart, then one
`SELECT count(*) FROM weave_vec_scan(idx, q, 10)` under
`EXPLAIN (ANALYZE, BUFFERS)`. 15 samples per (arm, run), **two runs per arm** (hard
rule 10), with arm order alternating per sample.

| arm | run | p50 ms | p25 | p75 | min–max | shared reads |
|---|---:|---:|---:|---:|---:|---:|
| v3 index | 1 | **1,143.7** | 1,100.7 | 1,150.1 | 1,033–1,154 | 19,166 |
| v3 index | 2 | **1,146.0** | 1,112.9 | 1,150.2 | 1,024–1,157 | 19,166 |
| v4 index | 1 | **835.5** | 772.6 | 840.6 | 738–842 | 12,916 |
| v4 index | 2 | **834.5** | 754.2 | 837.5 | 743–844 | 12,916 |

- **About 27 % lower p50 (1,145 → 835 ms), with 6,250 fewer page reads.** 6,250 is
  exactly the number of blocks: one page per block not read. The within-arm p50
  spread is 2.3 ms (v3) and 1.0 ms (v4), against a between-arm delta of 310 ms, so
  the difference is a result (hard rule 10).
- **Why it is faster, which the old spec text got wrong.** §7.1 said a scan that
  does not prune "never reads these pages at all". The shipped code cursor
  (`code_cur_block()`) read every one of a block's `strips_per_block` pages,
  centroid included, whether or not the bound pruned. So v3 paid 3 reads per block
  at 960-d and v4 pays 2. The note is now marked SUPERSEDED in place.
- **What this is not.** It is the flat `weave_vec_scan()` SRF, cold, on one
  `c7i.4xlarge` with gp3 storage. It is not the Phase V gate's latency (heap rerank,
  `ORDER BY` plan) and not a comparison against HNSW. The reduction should carry to
  any scan that reads whole blocks, in proportion to pages per block (3→2 at 960-d,
  2→1 at 384-d). **That is predicted, not measured.**

| the reader ignores the packed centroid (`weave_vecweft_page_take()` takes only the first strip of each page) | `weave_check(deep)` at 1,024-d and 960-d, 1 violation each | **not by the scan's answers**; see below |
| the writer packs a centroid that does not fit (fit check removed) | `CREATE INDEX` at 500-d: "could not build vector code page 0 of block 0" | the strip builder refuses a short destination, so this cannot write past the page |
| plan and reader disagree on the page index (cursor walks `strips_per_block` pages, not `pages_per_block`) | the scan at 1,024-d and 960-d: "cannot read bolt 0" | the cursor reads the next block's page and refuses it |

**A gap, stated rather than discovered later:** the first mutant left every scan answer
unchanged. The centroid is read only by bound (B3), the shipping scans pass
`-INFINITY` as the threshold, and B3 measured 0.00 % pruning (§8b). So a reader that
loses the centroid gets a wrong bound, never a wrong row, until a pruning scan exists.
Only `weave_check()` (its recomputation of the centroid) and the standalone tests catch
it. In the standalone layer, `test/hegel/test_vecweft.c` reported this mutant 21 times,
and also caught the other two plus a plan placing the centroid 4 bytes late.

### Standalone and fuzz

- `test/hegel/test_vecweft.c` runs at v3 and v4 over dims including 384, 500, 768,
  960, 1,000 and 1,024, all widths 2–8 at small dims, and partial blocks: **10,183,775
  checks, 0 failures.** Two new properties:
  - **P8 (hard rule 16):** a merge of any split of a lane sequence, with inputs at v3
    or v4 and split points on and off a block boundary, reproduces the code and
    directory pages of one v4 write byte for byte.
  - **P9:** a reader whose geometry disagrees about packing is refused, in both
    directions.
- `test/fuzz/fuzz_vecstrip.c` is new, under ASan+UBSan. It ran 654,078 random
  geometries (no strip placed past the page), every truncation of every page, and
  random corruption. Its teeth build (`-DWEAVE_VECWEFT_PLANT_NO_OFF_LEN`) aborts with
  a heap-buffer-overflow.
- `make check-standalone` and `test/fuzz/run.sh` both pass locally. **They were not
  run on EC2:** the smoke runs only the codec test. This is a local result.

### A test that v4 broke by being smaller

The smoke on `5469f6a` was red on `t/015_alloc_outcomes.pl` test 22, "weave_vacuum()
(AEL) reaches a smaller fixed point than plain VACUUM does". At its 2,000-row vector
fixture, the v4 index was small enough that plain VACUUM's first cycle reused 84 pages
the merge had freed, with zero extends. It landed on the floor, so both sides settled at
86 pages. Measured on one host (`pgweave-20261005-063541-9dc4`), same fixture:

| | plain VACUUM series | AEL fixed point |
|---|---|---:|
| v3 `.so`, 2,000 rows | 297 → 280 → 280 → 280 → 280 | 142 |
| v4 `.so`, 2,000 rows | 86 → 86 → 86 → 86 → 86 | 86 |
| v4 `.so`, 2,400 rows | 207 → 195 → 195 → 195 → 195 | 99 |
| v4 `.so`, 3,000 rows | 254 → 232 → 232 → 232 → 232 | 121 |

The fixture is now 2,400 rows (`e278db4`), with this table's numbers in a comment.
The fixed-point and zero-allocation assertions passed at every size.
