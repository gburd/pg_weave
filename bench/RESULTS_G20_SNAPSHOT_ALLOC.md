# G20 snapshot allocator: raw A/B/C measurement

**Date:** 2026-09-18. **Gap:** G20. **Host:** this workstation, PG 17.11 (nix),
`autovacuum = off`, `fsync = off`, `maintenance_work_mem = 256MB`,
`shared_buffers = 512MB`, scratch cluster on `/scratch`. A `nix build` of the TAP
check was running for part of the batches arms, so **wall clock here is recorded,
not claimed**; page counts are deterministic and contention-independent.

**This file records raw numbers only.** No ratios, no percentages, no "-N%", no
"Nx". The arithmetic and any claim derived from it belong to whoever reads this;
G20 in `doc/GAPS.md` is where a conclusion would go.

Same harness, same corpus generator and the same two arms as
`bench/RESULTS_G20_MERGE_GATE.md` (read its "What the two arms are" and "Exact
commands" sections first — everything there still applies, including why the body
is generated by a `LATERAL` with an outer reference).

## What the three arms of code are

- **extend-only** — `main` at `aaf21b8`, i.e. with the two serialization commits of
  this sprint but with `weave_merge_segments()` / `weave_merge_all()` still
  allocating `extend_only` for the whole merge loop.
- **snapshot, unbounded probe** — the snapshot allocator with no limit on how many
  candidates one scope may probe.
- **snapshot, bounded probe** — the shipped form: a scope that has probed
  `WEAVE_ALLOC_SNAPSHOT_PROBE_MAX` (64) candidates without a single reuse abandons
  its snapshot and extends for the rest of the scope.

Two runs of every arm. The two runs of each are reported separately; where a
number is given once, the two runs produced the same value **to the page**.

## Things a reader needs to know before doing arithmetic on the above

- **The two arms must not be compared to each other or averaged.** `fsm_defer` is
  ~113,000 in arm A and 0 in arm B: one transaction per document lets the xid
  horizon advance between commits, so the recycle gate clears freed pages instead of
  refusing them. They measure the allocator under two different reuse regimes. This
  is the same warning `RESULTS_G20_MERGE_GATE.md` carries, for the same reason.
- **A merge's reuse moved columns.** In snapshot mode a merge draws from the gathered
  list, so its reuse is counted in `lowfree_*` and its `fsm_reuse` is 0 *by
  construction*. The `fsm_*` numbers above are the segment writer's allocations, and
  they are identical across all three arms.
- **The bounded and unbounded arms differ on arm A and are identical on arm B.** In
  arm A a merge's snapshot is nearly all pages the merge's own transaction freed, so
  reuse is only found by probing deep into it; the bound declines to pay for that.
  In arm B the first candidates are already recyclable and the bound never triggers.
  The bound's constant (64) is a choice with both endpoints measured here, not a
  swept optimum.
- **`weave_vacuum()` reclaims to 2,029 pages in every arm A run**, byte-identical,
  so none of this changes what the index finally contains.
- Two runs per arm, one host, one corpus shape. Arm A's *extend-only* column
  reproduces `RESULTS_G20_MERGE_GATE.md`'s "after" column (353,181 vs 353,181 pages
  at batch 6; `fsm_defer` 113,544 vs 113,544), which is what validates the harness
  across the two sessions.
