# G20 insert-time merge gate: raw A/B measurement

**Date:** 2026-09-16. **Gap:** G20. **Host:** this workstation, PG 17.11 (nix),
`autovacuum = off`, `fsync = off`, `maintenance_work_mem = 256MB`,
`shared_buffers = 512MB`, scratch cluster on `/scratch`.

Page counts are deterministic and contention-independent, so a loaded workstation is
a valid host. Wall-clock times are recorded because the harness printed them, not as
a claim: this box was doing other work.

**This file records raw numbers only.** No ratios, no percentages, no "-N%". The
arithmetic and any claim derived from it belong to whoever reads this, and G20 in
`doc/GAPS.md` is where the conclusion goes.

## What the two arms are

**before** = `main` at 6d3d547, where `weave_insert_oversized_as_segment()` calls
`weave_merge_segments()` after every oversized document.
**after** = the same tree plus `weave_small_runs_worth_merging()`, which defers that
call until `WEAVE_MERGE_FANOUT` (8) smallest-level runs are waiting.

Corpus: `docs(id bigserial, body text)`, index `USING weave (to_wdoc('simple',
body))`. Every body is 1,660 terms drawn deterministically from a shared
50,000-term vocabulary — 1,660 distinct terms per document, ~11.25 KB of text,
which is over one pending page, so **every** insert takes the oversized-segment
path. Verified on the corpus itself before measuring:

```
 id | bytes | terms | distinct_terms
----+-------+-------+----------------
  1 | 11250 |  1660 |           1660
  2 | 11249 |  1660 |           1660
 50 | 11254 |  1660 |           1660
distinct_bodies = 50 of 50 rows
```

The last line is not decoration. The document body is generated by a `LATERAL`
subquery with an outer reference precisely because an *uncorrelated* sublink becomes
an `InitPlan` evaluated once, which would have turned 1,000 documents into 1,000
copies of one and made the whole measurement meaningless in a way no counter would
have shown.

## Exact commands

Relocate a writable PostgreSQL tree (the nix store is read-only) and install this
build into it:

```sh
PGSTORE=/nix/store/y37nxb0qmpjsqqh1mk5jbpl2h3f28qj9-postgresql-17.11
mkdir -p /scratch/pg17 && cp -rL "$PGSTORE"/. /scratch/pg17/ && chmod -R u+w /scratch/pg17
nix develop --command bash -c \
  'export PATH=$(ls -d /nix/store/*clang-wrapper*/bin | head -1):$PATH; make -s install DESTDIR=/scratch/stage'
cp -f /scratch/stage"$PGSTORE"/lib/pg_weave.so /scratch/pg17/lib/
cp -f /scratch/stage"$PGSTORE"/share/postgresql/extension/* /scratch/pg17/share/postgresql/extension/
```

Build the two shared libraries A/B, so the only difference between arms is the
compiled gate:

```sh
git stash && make -s -j8 && cp pg_weave.so /scratch/g20-before.so
git stash pop && make -s -j8 && cp pg_weave.so /scratch/g20-after.so
```

Then, for each `WHICH` in `before after` and each `ARM` in `batches percommit`:
stop the cluster, `cp -f /scratch/g20-$WHICH.so /scratch/pg17/lib/pg_weave.so`,
wipe and re-`initdb` `/scratch/g20data/pgdata` with the conf above, start,
`CREATE EXTENSION pg_weave`, and run

```sh
bench/ingest_amplification.sh $ARM     # NBATCH=6 BATCHSZ=1000 NPERCOMMIT=4000
```

`bench/ingest_amplification.sh` is in this repository and carries the method notes;
the swap driver lived in `/scratch/g20run.sh` and is reproduced above.

**Two facts to carry out of this table.** The post-vacuum page count is byte-identical
between arms — 2,029 pages both — so the gate changes how much scratch space the
ingest burns, not what the index finally contains. And `fsm_defer` stays at ~113,000
in both arms: the free list is still consulted and still refuses, because the
mechanism G20 identified is untouched. This is a mitigation of the rewrite rate, not
a fix for the XID gate.

**Cross-check against the original G20 run** (`RESULTS_INGEST_AMPLIFICATION.md`,
2026-09-14, different session, same method): batch 3 recorded 254,856 pages and
`fsm_reuse` 76; this run's before arm gives 255,372 and 76. 6,000 documents recorded
4,293 MB; this run gives 4,303 MB. The reproduction is close enough that the harness
in this directory can be trusted to be measuring the same thing.

## Arm B — 4,000 single-row transactions (worst case for segment minting)

One oversized document per transaction, so a new one-document segment per commit and
nothing amortised across rows. `weave_index_nsegments()` is sampled **after every
commit**, because the failure being guarded against is a spike and a final reading
would miss one.

| | before | after |
|---|---:|---:|
| commits | 4,000 | 4,000 |
| **max live segments** | **8** | **15** |
| min live segments | 1 | 1 |
| final live segments | 8 | 8 |
| pages | 271,083 | 127,248 |
| MB | 2,117 | 994 |
| `fsm_reuse` | 75,848 | 75,848 |
| `fsm_defer` | 0 | 0 |
| `extend` | 271,082 | 127,247 |
| wall clock | `real 6m26.777s` | `real 2m55.738s` |

`WEAVE_MAX_SEGMENTS` is 128. `t/007_segment_cap.pl` now asserts `<= 64`, on the
resting count and on the peak each inserter observed. In the `tap-pg17` leg that peak
came out at **15 from 4 concurrent inserters** (240 oversized documents), final
resting count 4 — independently reproducing arm B's 15 under a completely different
write pattern.

`fsm_defer` is 0 in both arms here and ~113,000 in arm A: one transaction per
document lets the xid horizon advance between commits, so the recycle gate clears the
freed pages instead of refusing them. That is the same discrimination G19's counters
were added for, and it is why arm A and arm B cannot be compared to each other.

## The claim in the port brief that does not hold for pg_weave

The upstream mitigation is described as behaviour-neutral below the threshold —
"below it the leveled compactor finds no level over capacity and is a no-op we can
skip". **That is false here, and the measurement shows it.**
`weave_merge_segments()` (`src/am/ambuild.c:3421`) has a *second* trigger: when no
level is over capacity but `meta.nsegments > WEAVE_MERGE_THRESHOLD` (8) it compacts
the lowest level holding two or more runs. Gating the call on level-0 occupancy skips
that trigger too, so the directory legitimately sits higher between merges — max
live segments moved from 8 to 15 in arm B, which is precisely the signature of a
gate that is *not* a no-op. (The same secondary trigger exists upstream, so the
upstream justification was also incomplete; upstream's own measured max of 15
against a previous ceiling of 8 is the same evidence.)

The replacement bound is structural rather than incidental: level 0 holds at most
`WEAVE_MERGE_FANOUT - 1` runs before the gate opens, and a merge invocation runs its
convergence loop — including the over-threshold trigger — until no level qualifies.
So the live count is bounded by roughly `WEAVE_MERGE_THRESHOLD + WEAVE_MERGE_FANOUT`,
i.e. ~16, and 15 is what was measured.
